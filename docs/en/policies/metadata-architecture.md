# Metadata architecture

**Durable design law for everything under "external metadata".** What we are building toward, and
which shortcuts are forbidden because they lead somewhere we have already decided not to go.

Today's implementation (`Packages/KinoPubMetadata` + `workers/tmdb-proxy`) is an early slice, **not
the shape of the finished thing**. Read "Target" before extending it; read "Known defects" before
assuming a behavior is intentional. Staged how-to and hosting:
[plans/2026-08-11-metadata-service](../plans/2026-08-11-metadata-service.md). Per-provider
capability sheets: [providers/](../providers/README.md).

## Product intent

We are building **an encyclopedia with a Plex-shaped layer on top**, which happens to stream through
kino.pub. Their contribution is a library, an account, and video delivery — an FTP with a player.
Everything a user looks at before pressing play is ours: artwork, credits, tags, collections,
similars, ratings from every source that has them, reviews, awards, trailers, dubs, per-episode
data, badges, and **where else this thing streams and in what quality**.

Two consequences that decide most arguments below:

- **Our catalogue is bigger than kino.pub's library.** Upcoming titles, titles that only stream
  elsewhere, and titles kino.pub dropped are first-class. A design that assumes every title has a
  kino.pub id is wrong on arrival.
- **A design that makes provider #7 cheap beats a design that makes provider #2 fast.** Field count
  grows without limit; latency budgets do not.

## Rule zero: document the source before touching it

**Before integrating a new source, and before extending an existing one, its schemas, methods, and
models are written down in full** — every endpoint the source offers us, every field, every model,
including the ones we have no intention of using. System automation and user integrations alike, no
exceptions.

This is not documentation hygiene, it is what stops the migration treadmill. Without it, every time
one more method is spotted the schema changes again. With it, "we already saw this endpoint and
decided against it" is a recorded fact instead of a rediscovery.

The corollary, and it is deliberate: **store every detail the API offers.** Which fields are
redundant gets decided later, from evidence about which source is better, faster, and more
complete — never at ingest time, and never by guessing in advance.

Sheets live in [providers/](../providers/README.md) and beside each provider module's code.

## Target architecture

### 1. The key is our own title id

External ids — `kinopub`, `imdb`, `tmdb`, `kinopoisk`, `tvdb`, `trakt`, `anilist`/`mal`, `apple` —
are **attributes with a confidence and a source**, never the primary key. kino.pub is one entry
point among several, not the spine.

```
title(id PK, kind, original_title, year, …)
title_external_id(title_id, namespace, value, confidence, method, resolved_at)
```

Entry points: `/v1/title/{id}`, `/v1/title/by/{namespace}/{value}`. The client holding a kino.pub id
asks by kino.pub id and never learns anything else about resolution.

**One universal method, asked in fields.** The client says which fields it wants and gets exactly
those; whether a field came from one source or six is our problem, visible in provenance and never
in the request. The client never names a provider, never branches on one, and never issues a second
call to find out what exists.

### 2. Catalogue, not lazy cache

We crawl and hold the whole thing, refresh it on a schedule, and **store raw before deriving**. Raw
provider payloads are kept per fetch so the schema can be re-derived later without re-spending
quota — the `tools/kinopoisk-metadata/probe.py` pattern, applied to every provider.

"Store first, decide what is redundant later" is the rule. Dropping a field at ingest time is a
decision that costs a month of re-crawling to undo; keeping it costs bytes.

Refresh cadence is per data class, not per title: identity is permanent, credits are near-permanent,
ratings/popularity/tops are daily-ish, availability and "new episode" are hourly for hot titles.

**Never re-crawl what already exists.** The kino.pub sweep, the tvoe pull, and the Kinopoisk pulls
were paid for once, in quota and in days. The first ingest is an **import** from those dumps; live
fetching starts from what is missing. Any new bulk source is imported the same way — a crawl is the
last resort, not the first move.

### 3. Two tiers, and the client only ever sees one

| Tier | Where | Holds |
| --- | --- | --- |
| **System of record** | VPS, Postgres | Full crawl, raw payloads per provider, the whole entity graph, jobs and their state |
| **Published read model** | Edge (Workers + D1/KV) | Compact per-title documents, identity map, image resolution map, tops and rows |

The client never queries the system of record, and the read model is never authored by hand — it is
regenerated by the pipeline. This split exists because a full crawl's write volume and a TV app's
read latency have nothing in common and should not share a database.

### 4. Images: the criterion is URL stability, not storage cost

Sources hold originals (TMDB, tvoe); the consumer asks for the size it needs. So we store **URLs**,
and the only reason to ever keep bytes is a URL we cannot rely on.

- **Stable origin URL → link to it.** tvoe's original URLs do not change, which is why the local
  pull exists at all. Same for TMDB paths.
- **Unstable URL → snapshot or proxy.** Resized/CDN-derived URLs that carry a release number or
  content hash (the Next-style resizer variants) break every re-crawl. Those are the ones that
  justify holding a copy — the hash, not the megabytes, is the problem.
**The proxy is mandatory, not optional.** `GET /img/{kind}/{size}/{namespace}/{id}` is the path the
client uses, always. Without it the client has no id but kino.pub's — no TMDB path, so no title
logo, no backdrop, no size variants, and no way to know an asset exists before asking. Answering
"here is the artwork for kinopub id N, at this size, and here is the fallback if the good one is
missing" is the entire job.

This holds until kino.pub's own responses are wrapped by our API too. At that point the wrapped
item carries a recommended artwork URL directly (`poster/big`, `poster/wide`), with the same
resolution and fallback chain behind it — the client's contract does not change, only who emits
the URL.

- The document also carries the **provider-canonical URL** for cases that want the origin.
- We host **only assets we created**: a replacement cover, a crop, a generated logo, an extracted
  average colour.

Per-source image notes belong in the provider sheets, because the differences are the whole point:
Apple is the strongest free artwork source; tvoe supplies curated Russian material specifically —
backdrops with no lettering, Russian title logos, short banner-style descriptions, and its own
badges — which is different data, not a duplicate of TMDB's.

### 5. Geography: two audiences, one API, minimal networking

Reality: kino.pub is Russia-facing (RU-only UI, no language switch) and its users already live
behind VPNs and tolerate latency. TMDB is reachable directly for everyone outside that mess.

- The API answers the same way for everybody: canonical URL **plus** proxy URL.
- The client probes origin reachability **once**, remembers the answer, and picks. That is the
  entire networking complexity budget — no per-region routing, no geo logic in the worker, no
  edge-node theatre for a network where our edge has almost no presence anyway.
- Non-RU clients therefore pay us for one JSON call and go straight to the sources. Which is the
  point: we are the index, not the pipe.

### 6. Per-field provenance and declared precedence

Merging is not "whoever answered first wins". Every field has a declared source order, and the
document records which source each field came from.

| Field group | Precedence |
| --- | --- |
| Cast / crew list, order, episode counts | International source (TMDB) → Kinopoisk → kino.pub |
| Russian character and person names | Kinopoisk → TMDB translations → kino.pub |
| Title logo, backdrop, poster | Apple/TMDB (language-scored) → Kinopoisk → kino.pub |
| Awards, facts, stills | Kinopoisk |
| Dubs / voice tracks, stream quality | kino.pub — nobody else has this at all |
| Ratings | **All of them, side by side, never silently averaged** |
| Availability, deeplinks | Per-service, each with its own `checked_at` |

### 7. Trust is a function of the title, not of the provider

- Do **not** trust kino.pub's baked-in credits for anything with an international match. Their five
  names on a thirty-season show are frequently stale junk.
- Do **not** trust Kinopoisk credits for a non-CIS title below a vote-count threshold — a
  low-budget German film with 100 votes has a thin, wrong, or empty cast there.
- Always ask the international source, **including for Russian titles**: it returns more per credit
  (episode counts, department, ordering, popularity) even when the RU source has the title.
- Ratings from a source with few votes are reported with their vote count or not at all.

### 8. People are entities, not strings

```
person(id PK, tmdb_id, imdb_id, kp_staff_id, name_en, name_ru, popularity, profile_path)
title_credit(title_id, person_id, department, character_ru, character_en, order, episode_count)
```

- The RU↔EN mapping is **built by joining on ids, never by matching names**. TMDB localizes the
  person `name` by `language` while keeping `id` stable, so two passes of the same endpoint
  (`en-US`, `ru-RU`) joined on `id` yield exact pairs — verified, see
  [providers/tmdb](../providers/tmdb.md#localization--how-the-russian-name-problem-is-actually-solved).
  Kinopoisk `/staff` supplies `nameRu` + `nameEn` on the same row, which is the second exact pair.
  (`also_known_as` does **not** carry the Cyrillic form — an earlier assumption here, disproved.)
- **Character names are TMDB's blind spot**: they stay English under `ru-RU`. Russian character
  names come from Kinopoisk, which is a large part of why that source is kept.
- Transliteration is a last-resort heuristic, never overwrites a known pair, recorded as low
  confidence.
- Matching people by normalized display name is a **temporary hack wherever it survives** — Cyrillic
  ↔ Latin never matches under name folding, and that is the whole problem.
- Keep roughly the top 30 credits by order/popularity **plus** every director, writer, and
  award-nominated person regardless of rank. Leads render in the cast rail; the rest in full credits.
- Awards and person pages both need stable person ids. That is the same table, which is why it is
  built once, server-side, and not re-derived per request.

### 9. Availability is an entity — and it is fetched on demand, late

Shape, when we build it:

```
availability(title_id, service, region, season, episode, kind, quality, formats,
             audio, subtitles, dubs, parental_rating, price_model, price, deeplink,
             available_from, available_until, checked_at)
```

`kind`/`price_model` covers subscription, rent, buy, and "already in your subscription". Streaming
services rent too, and titles *leave* — so rows carry a validity window and accumulate into a
history rather than being overwritten.

**But it is deliberately late and on demand.** Availability is the most volatile data in the whole
system and the least demanded early: we do not surface titles we cannot play first. Resolve it when
a user actually asks "where can I watch this", cache briefly, and never precompute it for the
library. Note also that per-user answers differ (a storefront can omit a service the user has not
installed) — which is why the paid aggregators exist. Do not go shopping for one; the shortlist
comes from the user.

### 10. Studios, tags, and signals are entities with a declared basis

- **Studio / network is an entity**, not a string on a title. "This is a Netflix original" is a
  badge, an icon on a card, and a filter — all of which need a stable id.
- **Tags are micro-genres** and there are tens of thousands of distinct ones in the wild. That is a
  feature: it is what makes similarity and recommendations possible later. Store them all; do not
  curate at ingest.
- **Signals are computed, stored, dated, and carry their basis.** A top is meaningless without
  saying what it ranks by — rating, recency, popularity, or view count (Netflix publishes all-time
  views *as* a rating). Two tops computed from different bases are different objects and never merge
  silently.
- "New season" needs the season's **end** date as much as its start.
- Computed by the pipeline into stored rows, never derived ad hoc in the client, never presented as
  live when it is a day old. Collapsing several services' top-30s into one list is a query over
  stored rows, which is only possible because they are stored.

### 11. Integrations: two kinds, one registry

Every external source is an **integration** with a declared capability descriptor: ids it accepts,
fields it can supply, auth owner, quota, cost, freshness class.

- **System integrations** are ours, invisible, run on our credentials and our quota.
- **User integrations** (Trakt, Plex, a personal Kinopoisk key) run on the user's credentials, never
  touch our quota, and are configurable and inspectable by that user.

Non-negotiable properties of the registry:

- **Every fetch is written through.** A request made to render a page also persists its raw payload
  and derived rows. Normal usage grows the library; the dedicated crawl is a backfill, not the only
  way data arrives. Burning a quota call and discarding the answer is the defect this whole design
  exists to kill.
- **"Did we already ask" is always answerable** — `fetch_log(provider, endpoint, key, status,
  fetched_at, ttl)`. Including misses. A repeat request into the void is a bug, not a cache miss.
- **Providers cannot block each other.** One queue, one rate limiter, one backoff, one health record
  per provider. A dead or throttled provider degrades its own fields and nothing else.
- **Errors are visible per provider** — last error, success rate, remaining quota — so a source can
  be revisited later and judged on evidence about what it is actually good for.
- **Nothing is deleted.** Raw payloads are retained and deriving is re-runnable; what is redundant
  gets decided later, on data, not at ingest time.

### 11a. One ingest path: raw first, derive second

Sources have nothing in common in shape, and unifying them at write time is what forces migrations.
So we do not unify at write time — we unify at derive time.

```
raw_payload(source, endpoint, key, via, fetched_at, body)   -- append-only, any shape
      ↓  one deriver per source, re-runnable
title / person / credit / rating / image / …                 -- the common entity graph
```

`via` ∈ `dump | donation | fetch`. **A dump row, a donated payload, and a live fetch enter through
the same function** — donation is not a special path, it is a raw payload with a different `via`.
That is what makes "populate one DB from many formats" a mapping problem instead of an architecture
problem, and it is `probe.py` → `ingest.py` from `tools/` generalized.

Schema change costs a re-derive, never a re-crawl.

### 11b. kino.pub content arrives by donation, not by crawling

The server has no kino.pub account problem to solve, because **the client already made the call and
already holds the payload**. After rendering, the app posts the non-personal slice of what it just
received to our API. Zero additional kino.pub requests, zero server-side auth on the hot path, and
coverage that follows what people actually open — with N users it scales by N.

- **Fire-and-forget.** Never on the render path, never awaited, failure is silent.
- **Whitelist, never blacklist.** Only named fields are sent. A field kino.pub adds later cannot
  leak by default. Watch progress, bookmarks, view marks, subscriptions, and per-user ratings are
  never sent, and the server has nowhere to put them if they were.
- **Counters are the freshness signal**, not noise: Kinopoisk/IMDb vote counts and kino.pub likes
  travelling with the donation tell us whether anything moved since we last looked, which is how a
  re-check is scheduled without polling.
**Two coverage classes, and donation only delivers one of them:**

- **Depth** — full documents for titles someone opened. Donation-driven, follows real attention,
  arrives free.
- **Breadth** — a **thin index over the entire kino.pub library**: id, title, original title, year,
  kind, external ids. Nothing else. This is what makes "take a 300-title collection from another
  service and show only what is actually watchable here" possible, and no amount of donation
  coverage substitutes for it, because intersection needs completeness, not popularity.

Breadth is cheap — it is an id list, not a catalogue — and it is the minimum needed to search other
providers, so it is held from the start even while everything else waits. A **system kino.pub
account** maintains it at a polite rate and backfills depth for titles nobody opened; it is a
background worker, not the primary path, and a single account cannot sweep 53k items of *detail*
without looking exactly like what it is.
- We do **not** relay the user's own kino.pub calls through our server. That would put us in the
  path of every screen, add latency to playback-adjacent requests, make the app depend on our
  uptime, and hand us personal data we deliberately refuse to hold — while buying nothing donation
  does not already give.

### 12. The user layer is ours; playback stays kino.pub's

We are responsible for **cheap metadata, enrichment, trailers, recommendations, and the collections
on the home screen** — making titles look good and be findable. That is the product.

We do **not** store watch progress or personal lists. That is a lot of data for something kino.pub
already holds correctly, and holding a second copy only creates a reconciliation problem. Streaming
URLs, quality flags, history, and bookmarks stay theirs and are never mirrored.

The only per-user state we keep is what a feature genuinely cannot work without and kino.pub has
nowhere to put — preferences that shape *our* surfaces (liked people/studios, muted genres and
sections) and notification subscriptions (a device token plus the title ids being watched for). Each
one is justified individually, or it does not exist.

Push notifications are the one feature that forces server-side per-user state (a device token and a
subscription list). That is a deliberate, bounded exception, not a licence to mirror the account.

### 13. Never blocking, never chatty

- The client paints the kino.pub payload first. Enrichment arrives later and only ever adds.
- One document per title per call. No GraphQL server; `?include=` trims, default is everything.
- The API answers with what is warm and refreshes the rest in the background. Stale beats spinner
  (see [data-continuity](data-continuity.md)).
- One in-flight request per key, on both sides.

## Rules for code written today

- **New providers land server-side, not in the app.** The app gets one more field, not one more
  network client. The in-app `MetadataSource` slot is for **user-keyed** providers only (Kinopoisk
  with the user's own key), because those calls must not run through our infrastructure.
- **The app models our merged document, never a provider's response shape.** A DTO named after a
  vendor does not belong in app code once that provider is behind our API.
- **Never key an app-side cache on a provider id.**
- **Never build UI that needs a second lookup to decide whether to render.** Sections hide on an
  empty field, not on a pending request.
- Any name-based matching added now carries a comment marking it as pre-`person` table.

## Known defects in today's implementation

Recorded so they are not mistaken for decisions:

1. **No IMDb id → no TMDB at all.** [TMDBSource.swift:84](../../../Packages/KinoPubMetadata/Sources/KinoPubMetadata/TMDB/TMDBSource.swift) returns early and
   [MediaItemModel.swift:309](../../../KinoPubAppleClient/Views/MediaItem/MediaItemModel.swift) does not even call the service. There is no `/search` fallback,
   and when one is added it must search by **original title + year** — a RU-title query returns
   nothing for obscure foreign films.
2. **Cross-alphabet cast matching is impossible.** `TitleMetadata.normalize` folds diacritics only
   ([TitleMetadata.swift:383](../../../Packages/KinoPubMetadata/Sources/KinoPubMetadata/Model/TitleMetadata.swift)), so «Реми Безансон» never matches "Rémi Bezançon"
   and every photo, character, and person id stays nil.
3. **Merge order is non-deterministic.** `MetadataService.metadata(for:)` consumes a task group in
   completion order and `merge` is gap-fill, so with two sources holding artwork the winner is
   whoever was faster that run. No provenance is recorded.
4. **Kinopoisk uses 5 of its endpoints** — `films`, `staff`, `awards`, `images?type=STILL`, `facts`
   — while `tools/kinopoisk-metadata/schema.sql` already models `box_office`, `videos`, `seasons`,
   `similars`, `reviews`, and `/staff/{id}` person pages. The app is behind our own offline schema.
5. **The kino.pub snapshot is thin.** `tools/kinopub-snapshot/data/snapshot.db` holds 53 485 items
   in 24 flat columns — no genres, tags, collections, seasons/episodes, dubs, or cast, and
   documentaries/concerts were skipped. It is a title index, not a catalogue.
6. **No ratings model.** `TitleMetadata` carries no ratings at all, per-title or per-episode.
7. **Cache is per-device and volatile.** `Caches/KinoPubMetadata` is purged on tvOS whenever the app
   is not running, so every cold launch re-spends third-party quota on the same titles.
8. **The worker is a dumb forwarder.** No identity storage, no merge, no image route — it only hides
   the TMDB token and edge-caches the passthrough.
9. **Person photos come from an MD5-of-name CDN guess** (`ActorImageProvider`), which works only
   because the hash is over the RU name we already have — a workaround for defect 2, not a source.
